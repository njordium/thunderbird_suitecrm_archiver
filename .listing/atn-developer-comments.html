The two files flagged in 0.2.2 src/icons/icon.svg and src/ui/release-notes.html are gone from the package. Both were genuinely unused: the SVG is the drawing the icon generator was written from rather than an input it reads, and the HTML fragment stopped being loaded when the settings page moved to reading release-notes.json instead of assigning HTML. The packaging step includes everything under src/, which is how they travelled. The drawing now lives outside src/, the fragment is no longer generated, and the build fails if any file under src/ is unreachable from the manifest, an import, an HTML reference or a getURL() path, the check reproduces exactly those two lines when the files are put back. 43 files ship now, down from 45. Thank you for the pointer to --llm-review. Our own use of webext-linter had been filtering its output down to failures, which discarded the two [unsure] escalations that this finding came from. It now shows the extended manual review section as well. Source and build
  • There is no build step. What is in the repository is what ships in the .xpi, file for file.
  • No dependencies, no bundler, nothing minified or generated. Every line is readable as written.
  • Released under the Mozilla Public License 2.0, the same licence as Thunderbird. LICENSE is included inside the package.
  • Manifest V3. Requires Thunderbird 140 ESR or newer.
Why the validation report shows warnings The store's validator checks against Firefox's schema, and Firefox has no mail. Every Thunderbird-only permission and API it flags is valid: messagesRead, accountsRead, messagesUpdate, addressBooks, messagesTags, messagesTagsList and compose are all in Thunderbird's own permission list, and messages.*, accounts.*, messageDisplay.*, compose.* and addressBooks.provider are all documented Thunderbird APIs. Thunderbird's own webext-linter reports no errors, warnings or info findings. What it does leave is manual-review items, and the substantive one is the three fetch() call sites it lists under user-data exfiltration: they are the CRM requests themselves, addressed to the host the user enters in Preferences and reached only after that user signs in there, which is also what the two data_collection_permissions declare. Verification
  • 296 unit tests, and 51 end-to-end steps across two scripts that run against a live SuiteCRM instance.
  • Zero eslint errors, and a manifest validator that fails the build if the content security policy override or a deprecated key regresses.
  • All of it is in tools/ and runs with npm test and ./tools/review.sh.
Reporting a problem Issues and questions: github.com/njordium/thunderbird_suitecrm_archiver/issues. Settings has a Create debug report button that produces a shareable file with secrets removed and addresses and hostnames masked by default, which is the fastest way to get a connection problem diagnosed.
